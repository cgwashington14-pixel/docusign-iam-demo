101 — How a request actually moves

One teaching path, not the live CLM canvas. A business user starts an internal request. It routes for edits and approvals, goes outside for redline, then comes back so you can map anything that changed before final processing. Play it once. The three data stores below are the whole trick.

Internal request → approvals → external redline → remap → close

Business users follow the people. Admins follow the step and which store it reads.

  1. 1 Request Internal form / Doc Gen
  2. 2 Edit Review Data, versions
  3. 3 Approve Internal Approve / Reject
  4. 4 Redline External review
  5. 5 Close Remap · sign · Finish

Where this path usually breaks

Click a row to jump that stage. These are configuration gaps — not Support cases — until a published design still fails the same way in UAT and prod.

  • Request · form never becomes metadata Doc Gen values sit in Params. The attribute panel stays blank. Later Decisions that read “Company” from attributes get empty. Fix: map with Update Document Metadata Value. Harvest TemplateFieldData schema from an empty test workflow first.
  • Edit · Review Data vs the Word file Required attributes block the task. A user can also upload a new version on Approve. The workflow variable does not move. Fix: Find Document after any human metadata or version change, then Update Variable Value from current metadata — not from Params.
  • Approve · missing Rejected (or stale condition) Internal Approval with only an Approved line stalls on Reject. A Decision that still reads the kickoff variable ignores the name Legal just corrected. Fix: draw every output; refresh before the Decision.
  • Redline · wait outputs and file limits Official: pair Review and Send for External Review with Wait for External Review. Wire Completed with Document, Completed without Document, Expired, Failure, and the Cancelled paths. Send for External Review fails if you send more than 10 files; combined size ≤ 25 MB; email ingest is PDF/DOCX. A Word redline is a new version — it does not automatically rewrite CLM attributes.
  • Close · skipped remap, then false Complete Coming back inside, Find Document so XML matches the new version, then map attributes that actually changed. Salesforce shops: Data Reconciliation is recommended after signature, not as a substitute for CLM metadata. Put Finish on every success path so Activity cannot lie and a parent can resume.

Capabilities this path is showing

Doc Gen kickoff, human Review Data and Approve (including version upload), Routing/Choice, External Review to a non-CLM user, version ingest, Find Document refresh, attribute mapping, eSignature, Finish. That is CLM’s native negotiation loop — not a custom integration.

The one rule for Params

Official: keep Params as the exact trigger payload. Copy it if you need to transform. After edits or redline, current truth is the document (attributes + latest version XML), not Params. If a Decision still looks at Params, it is answering “what did they type on day one?”

Diagnose from the Activity panel

CLM (the product formerly branded SpringCM) records every instance under Admin → Automation Tools → Workflows. The Activity tab is the source of truth — not the document’s folder, and not a user’s memory of “where it died.” Play the walkthrough first so the screens below match what you will click.

Executing

Waiting or blocked

Human step: someone has a task. Automated step: permissions, XPath, connector, or no outbound path. Pause to inspect; abort to clear tasks.

Complete

Confirm it really finished

Without a Finish step, a dead instance can still show Complete. Finish is also required for a parent workflow to resume.

Walk the instance

  1. Open Activity. Admin → Automation Tools → Workflows (the page opens on the Activity tab). Filter by Workflow, Last Updated, and Workflow Status (Executing, Failed, Aborted, Complete, and others your account lists).
  2. Open the instance, then Execution View. Click the instance name to open it in the designer. Use the Execution View icon (upper right) to see the current step and live variable XML. Do not treat the Configuration canvas as the running instance until you are in Execution View.
  3. Read the Activity Panel on the failing or current step. Connector system/provider errors land here — missing fields, invalid types, credentials, object permissions.
  4. Inspect XML variables — especially Params (incoming content) and any Document variable. Copy the node path; do not guess from the UI label.
  5. Check Logger steps if the design includes them. Logger writes a message into the workflow monitor and is the cheapest way to see which branch ran.
  6. Pause vs abort (for in-progress instances). Pause suspends automated steps and does not cancel them — you can resume from the current step. Abort cancels in-progress automated steps and human tasks so they leave the Tasks page; you then start a new run from the beginning. A Failed instance is already stopped — fix configuration, publish, and start a new instance.
False Complete Docusign documentation: if a workflow without a Finish step stops at “Approve 1” because of a failure, Activity can still show Complete. With Finish on the canvas, the same run shows Failure. Always put Finish on every successful end path — you can have more than one.

Reports when Activity is noisy

  • Workflow Summary (enable Enable workflow summary reports in Account Settings) — longest stage, most common failed/aborted/executing stage. Official docs: these workflow reports include only workflows that contain human steps; fully automated processes are omitted.
  • Workflow Step report — Docusign Community guidance when a Failed instance is missing from a Workflow Overview report: Step-level reports are usually more granular. Set a distinct Stage Name on human steps so two Approvals do not collapse into one label.
  • Set Workflow Process Name — the name that appears on workflow reports (for example in a Workflow Steps report). Use it when many instances share one design. On a parent/child pair, docs say you only need to set it on the parent.

Attributes, company data, and Params

Most “the workflow has the wrong value” tickets are a confusion between three stores: document/folder metadata (attributes), the incoming Params XML, and workflow variables. They are not kept in sync unless you design them to be.

Document attributes Metadata on the file. Workflow designer calls this “metadata value.” Searchable and shown on the document.
Folder attributes When every document in a folder shares a value (for example Country = United States). Update Folder Metadata Value.
Company / party data Not a separate official object type. Counterparty values usually live in a document attribute group you named (often “Company”) or in party / Actor XML — they are not automatically the same as document metadata.
Params XML Incoming content that triggered the run (Doc Gen, custom start parameters, document kickoff). Do not overwrite it.

Why the workflow still has the old company name

Attribute and variable start equal, then Review Data edits only the attribute. Play this before you “fix” a Decision that looks wrong.

Workflow variable Acme LLC
Document attribute Acme LLC

They match at kickoff. They are not kept in sync unless you design that.

Attribute ≠ variable

They may start equal (you wrote one from the other) and then diverge after Review Data or a user edit. To read the current attribute, Find Document (refresh the document XML) then Update Variable Value from that metadata. Execution View shows the path; Community examples look like <%#Doc.Group.Field%>.

Never mutate Params

Official guidance: keep the exact trigger payload for debugging. Copy Params into a working XML variable if you need to transform it. Custom start parameters are pasted on Start Workflow → Provide custom parameters.

Review Data

Assigns up to 50 document attributes to a user or task group. The task cannot complete until every required field is filled — a “stuck” workflow is often a required attribute the assignee cannot see or does not understand.

Doc Gen fields are not attributes

Values the user typed on a generation form sit under Params → TemplateFieldData. They will not appear in the document’s left-hand attribute panel until Update Document Metadata Value maps them.

XML, XPath, and how to pinpoint the node

CLM workflow data is XML. Trainers describe configuration as “navigating nodes”: every Decision, metadata write, and Doc Gen mapping needs an exact path, not a nearby label.

Params and TemplateFieldData

The default incoming variable is named Params (you may rename it). For document generation, a TemplateFieldData node holds the form field values. Official docs: that schema is empty until an associated Doc Gen configuration has triggered the workflow at least once — harvest schema from a throwaway empty workflow, then add it to the real design.

Illustrative Params shape after Doc Gen (field names come from your form) 
<Params>
  <TemplateFieldData>
    <Department>Procurement</Department>
    <ContractValue>250000</ContractValue>
    <CompanyName>Northwind LLC</CompanyName>
  </TemplateFieldData>
  <!-- Document / folder kickoff payload also lands here -->
</Params>

# Evaluate XPath source: Params
# /Params/TemplateFieldData/Department
# /Params/TemplateFieldData/CompanyName

Evaluate XPath

Source variable can be Params, a document XML, a folder XML, or any custom XML with a schema. Output types: Boolean, Number, String, or Node Set. If the step “works” but downstream is empty, you evaluated the wrong variable or an XPath that does not exist on this instance’s XML (namespace, repeating group, or a field the user left blank).

Analyzer / scorecard example from Docusign docs 
//ScorecardElement[./Topic/text()='Indemnification' and ./RiskLevel/text()='High']

Bulk metadata XML

Update Document Metadata Value and Update Folder Metadata Value accept an XML method for bulk updates and attribute-group deletions. Official docs: use the documented bulk-metadata XML schema (PATCH or PUT update types). Find Document output is the usual baseline (groups and fields as repeating / non-repeating sets). Large static sets can load via Update Variable From XML; dynamic sets often go CSV → C# expression → XML variable. Create Variable from CSV limits: CSV file ≤ 1 MB in a CLM folder, resulting XML variable ≤ 5 MB, header row, at least two columns.

JSON ↔ XML Convert JSON to XML (and the reverse) when a connector returns JSON. Some XML-to-JSON conversions need Newtonsoft’s namespace plus json:Array='true' on a node so a single element still serializes as an array — otherwise HTTP bodies fail schema checks and the connector looks “randomly broken.”

Routing and workflow configuration

Wrong path is a configuration attribute problem: conditions, connector outputs, assignees, and due dates. Walk the lines on the canvas the same way you walk the instance.

Missing Rejected path — the silent stall

Trainers flag Internal Approval with only an Approved line as a top production failure. The engine has nowhere to go on Reject.

Internal Approval
Approved Finish
Rejected No destination
Step What it does Where it breaks
Decision If / Else on a condition. Each branch has a string output (example: Standard vs Non-Standard). Condition uses a stale variable; quoted strings have extra spaces; Else never configured so unmatched values stall.
Rule Condition → True or False. Same as Decision — plus no line drawn from False.
Routing Human picks the next path. Options can be a dynamic pipe- or comma-delimited list. Empty option list. Official: commonly followed by a Decision when the choice should change the path — skip Decision if every option goes to the same next step (for example the same approval, different task group).
Choice Human picks from a fixed list (Approve / Reject / Route to Legal). No outbound line for Reject or Step Cancelled.
Connector lines Every prior-step output must go somewhere (Updated, Success, Edited, Reviewed, Approved, Rejected…). Trainer tip: Internal Approval without a Rejected pathway is a top production failure.
Assignees User, task group, or Resource Variable (Actor XML from email / GUID / group). Email is not a CLM user; task group empty. Resource Variable: Expand Groups must be checked when the input is a group name or group ID (loads Actor XML).
Due date / cancel Due Date Action times the task out (Timed Out path). Enable Step Cancellation requires a Step Cancelled path. Timeout follows Timed Out, not automatic Failure. Cancellation with no Step Cancelled path could cause workflow failure (official wording). With Use business days only, specifying 1 day equals 3 business days because CLM measures a business day as 8 hours (so 2 business days = 16 hours).
Link to next step Optional on human steps: jump the same user to the next human step. The next human step must be assigned to that same user. Waits grow with automated work in between — reduce those steps or optimize the path. Do not enable this on the last human step.

Rogue spaces in CSV, attribute names, or file paths Very common

Trainer Derval Lynes (Docusign University): trailing space after a CSV header (Department ), extra space on an attribute field name, or a space in a folder/file path means CLM cannot read the column, map the attribute, or find the file.

Fix: Re-type the name, or copy from Admin with no trailing space. Re-save the CSV. Correct the path. Republish.

Workflow not fully published Silent

Save icon → Publish icon → click the Publish hyperlink. All three. A saved-but-not-published design is what ran yesterday, not what you just edited.

Fix: Complete the three-step publish, then start a new instance. Do not debug the old instance against the new canvas.

Connector: permissions, credentials, required fields, data type

Activity Panel lists system/provider errors. Connector user needs object permission (example: NetSuite customer object). Manage Connection to rotate credentials — that does not rewrite workflows. Add required fields including custom-required fields on the record. Match date/number/picklist formats.

CSV missing emails / not CLM users

Official: Update Variable from CSV follows Failure when the Search Field Value is not found in the Field Name column (first matching row wins if the lookup column is not unique). The CSV needs a header row, at least two columns, and must live in a CLM folder. Trainer tip: blank approver emails, or addresses that are not CLM users, break later assignee steps that read those columns. File size ≤ 1 MB / resulting XML ≤ 5 MB apply to Create Variable from CSV, not this lookup step.

XPath returns empty

Wrong source variable, schema not populated (Doc Gen never triggered this workflow), repeating node vs single node, or a blank form field. Open Execution View XML and test the path against this payload.

No Finish step — status can lie Official docs

Engine Workflow Steps: if a workflow without a Finish step stops at “Approve 1” because of a failure, the activity monitor can still show Complete. With Finish on the canvas, that run shows Failure. A parent waiting on this child does not resume until Finish is reached.

Update Variable Value: partial or silent miss

Official outputs for this step: Updated (all variables succeed, or at least one succeeds while others fail without exceptions), Not Updated (every update fails without exceptions), Failed (any update throws an exception). If some variables miss silently, split into one Update Variable Value step per variable so Activity shows which one broke.

Step cancellation with no outbound path

If Enable Step Cancellation is on, you must define a Step Cancelled path. Official wording: otherwise cancellation could cause workflow failure.

Best practices (from Docusign docs and trainers)

Design so you can diagnose

Finish on every success path. Logger before/after Decisions. Meaningful Step Description (shows in the designer and process monitor). Start step: error email + “Track and record workflow activity.” Distinct Stage Names for reports.

Publish like production

Clone before editing a live workflow. Save → Publish icon → Publish link. Test in UAT (including Test Reminder on human steps). If a step is corrupt, delete and rebuild it rather than incrementally patching for more than a few minutes.

Keep data stores honest

Find Document after any human metadata edit. Copy Params before transforming. Map Doc Gen → attributes explicitly. One variable update per step when debugging. Harvest Doc Gen XML schema from an empty workflow first.

Draw every line

Approved and Rejected. Success and Failure. Timed Out and Step Cancelled. Else on Decisions. Resource Variable + Expand Groups when assigning from a security group.
